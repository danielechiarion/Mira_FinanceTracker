## Cryptography
Data encryption is handled using libraries implementing the AES algorithm, for better perfomance than asymmetric encryption. 
The data saved inside the application are local and not shared with third-party services, a part from the implementation of Google Drive backup selected by the user. 

Inside the application it's proper to distinguish two different types of keys:
- **System key** used to cypher system database and save data which are local inside the application
- **User key** used to cypher private user data and cloud backup inside Google Drive, when enabled. Each user has a different user key. 

### Cryptography key specifics
Both system and user cryptography keys are based on a 256-bit AES-GCM algorithm, generated with a nonce of 96 bits and MAC of 128 bits.

*But it was found that the user key required another layer of security because, in case of possible cloud implementation, the cryptography key would have been shared through cloud. So it was proper to make it accessible only for authorized user and devices.*
Because of this requirement, the user key is enwrapped a so called "locker-key" made to keep the operative cryptography key safe. So the locker key is generated by:
- PBKDF2 con HMAC-SHA256 algorithm
- Passkey given by the user or randomly generated by the system (12 bytes suggested at least).
**The output is another 256 bit key.**

### Key saving system
Private and system keys are saved inside two different locations:
- **FLUTTER SECURE STORAGE** encrypted storage developed for flutter developed completely by the hosting operating system. This will allow both system and user keys to be safe. 
In particular, the data will be saved using as keys `cryptosystem_database` for system key and `cryptouser_<USERNAME>` for user key. Each value is an encoded JSON following the format:
```json
"SYSTEM_KEY" // for the system key there is only the final key

/* structure of a user key with the elements described before.
All data inside the encoded JSON are not encrypted,
because they are already protected by the secure storage */
{
  "lockerKey": "<LOCKER KEY>",
  "userKey":   "<USER KEY>",
  "salt":      "<SALT>",
  "password":  "<PASSKEY GIVEN BY THE USER>"
}
```
- **GOOGLE DRIVE SPACE** accessible only if it is enabled by the user. The file containing the key, saved in a specific folder, following the JSON format:
```json
{
  "username": "<username>",
  "salt":     "<original salt>",
  "userKey":  "<user key encrypted by nonce and passkey + mac>"
}
```
When importing the key, the program will ask to the application the passkey chosen during signup procedure and, starting from this input, the user key will be decrypted from locker key and will be available to read or write data for the same users in different devices.
***The key importing procedure is essential to avoid corrupted data and communication between devices***.

### Cryptography limitation
The cryptography key is built to cypher both database and cloud data for each user. 
Mobile applications can implement `sqflite_sqlcipher` to protect data, while this function in not available for desktop applications. 
So, when running the application on computer, the database will contain clear data, without any encryption. 


## Database
The database system uses SQL language and will be divided into 2 diffent categories of databases:

### System database
The system database saves informations related to account credentials, which are local and not available for the single user. This database is encrypted following the [cryptography](#cryptography) and [its limitations](#cryptography-limitation) explained before. 
The main tables for the system database are:
1. `User` table with the user credentials registerd (password is hashed)
2. `GoogleAuthSession` table saving the session of each google account, to handle multiple account connection. 

### User database
Database to save private information of the user. Each user has its own database with filename `user_<USERNAME>.db`. This database is encrypted following the [encryption specifics](#cryptography-key-specifics) explained before.
The tables for the user database are:
1. **SUBJECTS** interacting with users operations, such as `FinancialInstitute` and `CounterParty`.
2. **BANK ACCOUNTS** the main table is `BankAccount` containing general information *and the unique ID*. Then the details of each type of bank account are expressed in the tables: `CurrentAccount`, `SavingsAccount`, `Card`.
3. **TRANSACTIONS** general entities to define financial movements connected to financial products or periodic billings. They are divided in `Income` and `Outcome`.
4. **PERIODIC TRANSACTIONS** divided in billings, such as `Cashback` and `BankFee` which are common to all bank accounts, and periodic transactions, such as `PeriodicIncome` and `Domiciliation` which are designed for current accounts.
5. **FINANCIAL INSTRUMENT MODELS** models of financial services to use throughout the products registered. They are divided in `TimeDepositModel` and `BondModel`.
6. **FINANCIAL INSTRUMENTS** services saved by the user specifically designed for the savings account. The can be created starting from a mdoel and they are `TimeDeposit`, `Bond` and `Stock`.
7. **STEP INTERESTS** entity which indicates an interest coming after a period selected. It is useful when the interest is variable and in entites like bonds. The tables are `StepInterestModel` for bond models and `StepInterest` for bonds.
