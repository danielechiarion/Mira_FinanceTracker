# Technical analysis
This section covers how the application is designed, looking at the tools and resources used and at the strategies to keep the software efficient and the data safe.
To understand the entity structures and the logic diagram of the application, please visit [Diagramma logico - Mira.svg](./Diagramma%20logico%20-%20Mira.svg) and [E_R Mira.svg](./E_R%20Mira.svg).


## Cryptography
Data encryption is handled using libraries implementing the AES algorithm, which offers better performance than asymmetric encryption. 
The data saved inside the application are local and not shared with third-party services, apart from the Google Drive backup, if selected by the user. 

Inside the application it is proper to distinguish two different types of keys:
- **System key** used to cipher the system database and to save data which is local to the application
- **User key** used to cipher private user data and the cloud backup inside Google Drive, when enabled. Each user has a different user key. 

### Cryptography key specifics
Both system and user cryptography keys are based on a 256-bit AES-GCM algorithm, generated with a nonce of 96 bits and a MAC of 128 bits.

*But it was found that the user key required another layer of security because, in case of a possible cloud implementation, the cryptography key would have been shared through the cloud. So it was proper to make it accessible only to authorized users and devices.*
Because of this requirement, the user key is wrapped in a so-called "locker key" made to keep the operative cryptography key safe. The locker key is generated by:
- PBKDF2 with HMAC-SHA256 algorithm
- Passkey given by the user or randomly generated by the system (at least 12 bytes suggested).
**The output is another 256-bit key.**

### Key saving system
Private and system keys are saved in two different locations:
- **FLUTTER SECURE STORAGE** encrypted storage for Flutter, handled entirely by the host operating system. This will allow both system and user keys to be safe. 
In particular, the data will be saved using `cryptosystem_database` as the key for the system key and `cryptouser_<USERNAME>` for the user key. Each value is an encoded JSON following the format:
```json
"SYSTEM_KEY" // for the system key there is only the final key

/* structure of a user key with the elements described above.
All data inside the encoded JSON is not encrypted,
because it is already protected by the secure storage */
{
  "lockerKey": "<LOCKER KEY>",
  "userKey":   "<USER KEY>",
  "salt":      "<SALT>",
  "password":  "<PASSKEY GIVEN BY THE USER>"
}
```
- **GOOGLE DRIVE SPACE** accessible only if it is enabled by the user. The file containing the key is saved in a specific folder and follows the JSON format:
```json
{
  "username": "<username>",
  "salt":     "<original salt>",
  "userKey":  "<user key encrypted with nonce and passkey + mac>"
}
```
When importing the key, the program will ask the user for the passkey chosen during the signup procedure and, starting from this input, the user key will be decrypted using the locker key and will be available to read or write data for the same user on different devices.
***The key importing procedure is essential to avoid corrupted data and communication errors between devices***.

### Cryptography limitation
The cryptography key is built to cipher both the database and the cloud data of each user. 
Mobile applications can implement `sqflite_sqlcipher` to protect data, while this function is not available for desktop applications. 
So, when running the application on a computer, the database will contain clear data, without any encryption. 


## Database
The database system uses the SQL language and will be divided into two different categories of databases:

### System database
The system database saves information related to account credentials, which is local and not available to the individual user. This database is encrypted following the [cryptography](#cryptography) and [its limitations](#cryptography-limitation) explained above. 
The main tables of the system database are:
1. `User` table with the registered user credentials (the password is hashed)
2. `GoogleAuthSession` table saving the session of each Google account, to handle multiple account connections. 

### User database
Database to save the user's private information. Each user has their own database with the filename `user_<USERNAME>.db`. This database is encrypted following the [encryption specifics](#cryptography-key-specifics) explained above.
The tables of the user database are:
1. **SUBJECTS** interacting with users' operations, such as `FinancialInstitute` and `CounterParty`.
2. **BANK ACCOUNTS** the main table is `BankAccount`, containing general information *and the unique ID*. Then the details of each type of bank account are expressed in the tables: `CurrentAccount`, `SavingsAccount`, `Card`.
3. **TRANSACTIONS** general entities to define financial movements connected to financial products or periodic billings. They are divided into `Income` and `Outcome`.
4. **PERIODIC TRANSACTIONS** divided into billings, such as `Cashback` and `BankFee`, which are common to all bank accounts, and periodic transactions, such as `PeriodicIncome` and `Domiciliation`, which are designed for current accounts.
5. **FINANCIAL INSTRUMENT MODELS** models of financial services to use across the registered products. They are divided into `TimeDepositModel` and `BondModel`.
6. **FINANCIAL INSTRUMENTS** services saved by the user, specifically designed for the savings account. They can be created starting from a model and they are `TimeDeposit`, `Bond` and `Stock`.
7. **STEP INTERESTS** an entity which indicates an interest arriving after a selected period. It is useful when the interest is variable and for entities like bonds. The tables are `StepInterestModel` for bond models and `StepInterest` for bonds.


## User preferences
User preferences define the settings that can be configured by the user inside the application. User preferences can be divided into two categories:
- **GLOBAL PREFERENCES** which are the same across all applications.
- **LOCAL PREFERENCES** which are used only inside the local application.

Local preferences are saved in the database when the user is disconnected and are moved to shared preferences (a memory slot integrated into the Flutter framework).
Global preferences also use part of the drive space to export the settings. 

Examples of preferences are:
- ***Enable background*** setting to enable background tasks inside the operation (GLOBAL).
- ***Enable notification*** setting to enable notifications for the local application (GLOBAL). 
- ***Backup time*** time, generally expressed in hours, to repeat scheduled tasks (LOCAL).

User preferences can support more settings than these, and they can be integrated into the environment as well.


## Cloud backup implementation
This application gathers all the financial information about a user, who would probably like to use it both on a mobile device (to register small payments and immediate transactions) and on a desktop (to have a better view of the financial situation).
So, implementing a cloud backup is the best choice to exchange the same information between multiple platforms, which are already supported by the Flutter framework. 
Because it was difficult for the developer to build a public database in which to save application data and keep it safe, it was decided to **provide cloud backup functionality on Google Drive**. Moreover, the framework, which is developed by Google, includes importable packages to communicate directly with this service. 

But, considering how important this functionality is for the application, there were different aspects to take into account: 

### Limitations
First of all, there are some limitations that could arise from this design:
- ***MULTIPLE SESSION HANDLING*** Potentially, two application instances connected to the same backup point could be executed simultaneously. But, in this case, the two applications could make different changes to different data or, possibly, to the same data. So, when the time comes to save the changes, **which session do we have to consider**? Because it is difficult to handle a correct merge of resources (like the function GitHub implements), especially in an encrypted database, *a user connected to the cloud will be able to use just one application instance at a time*. This can be done by creating a file inside Google Drive in order to lock the space, registering which session is working at the moment.
- ***BACKUP FREQUENCY*** Knowing how often an application should back up information is another key point of this functionality. A backup and cross-device application should always have the most up-to-date data registered in its instance. But the application is serverless and it is difficult for it to open a background process to update and save data when a change occurs, because operating systems (in particular mobile ones) do not precisely respect the time to accomplish the task, since they have to work according to power-saving and system security policies. *This is why the application performs the cloud import every time the application resumes or opens and saves the content every time the application pauses or stops*.
- ***DATA SECURITY*** The application will save data in a private folder inside Drive, accessible only by the instance and not by the common Drive interface. All the files regarding user preferences and the database are encrypted following the [cryptography design](#cryptography) explained above.
- ***MULTI-USER*** inside Google Drive it is possible to enable multi-user backup, but this would require a heavy structure, struggling to handle different keys and encryption. Because of that, the Google Drive space will host the backup of just one user.
- ***CONNECTION AND CLOUD OPERATIONS*** implementing Google Drive backup requires a stable Internet connection. Besides, cloud operations could produce errors when reading, writing or when trying authentication. In these cases, it is possible for the user to disconnect the account from the cloud and interact offline. Then it will be possible to connect to the cloud later, repeating the whole account procedure. This prevents the account and the application from being blocked by a cloud error. 

### Sessions
The sessions are used inside the backup space to let the others know which device and user are interacting with the drive. 
The available sessions have been divided into two types:

#### FOREGROUND SESSION
Indicates the session when the application is launched. The file saved in Google Drive follows the format:
```json
{
  "user": {}, // map object containing the user
  "os": "<OS_NAME>", // name of the OS
  "deviceModel": "<DEVICE_MODEL>", // model of the device
  "deviceName": "<DEVICE_NAME>", // name of the device
  "accessTime": "<ACCESS_TIME>" // time when the application accessed the drive
}
```
This file is not encrypted because it is the first thing an application should check, even before reading the cryptography key, because this operation is useful only when it is possible to read and write inside the files.
**When a foreground session is registered, no other application instance can be used. When the application session is finished, the file is removed or emptied**.
*When the application is running, the file containing the background session is read as well. Since a background operation is planned and is designed to update expiring dates and expected transactions, it is better for the foreground session to wait until the open background session ends, in order to have updated information*.

#### BACKGROUND SESSION
It is the session related to an opened background task. The background session is essential for the application to share results when the task has ended and to prevent different application instances from running the same task. The file saved in Google Drive follows the format:
```json
{
  "user": {}, // map object containing the user
  "os": "<OS_NAME>", // name of the OS
  "deviceModel": "<DEVICE_MODEL>", // model of the device
  "deviceName": "<DEVICE_NAME>", // name of the device
  "accessTime": "<1900-01-01 00:00.0000>", // time when the application accessed the drive
  "endingTime": "<1900-01-01 00:00.0000>" // time when the last background task finished (it could be empty if the task has not finished)
}
```
The file contains the ending time, which indicates when and whether the background task has finished. 
The file is not encrypted and is not deleted after the session ends, because the background tasks should know when they should act or not. In particular, **a background session should start when the previous task has finished at the previous scheduling time, or when the background task has started and has not finished within a specified time.**

### Backup file organization
Inside the private Google Drive `appDataFolder`, the backup files are organized as follows:
```
appDataFolder/
├── background_session.json
├── foreground_session.json
├── device_register.json
├── crypto/
│   └── crypto_key.json
├── preference/
│   └── preferences.json
└── database/
    ├── counter_parties.json
    ├── financial_institutes.json
    ├── bank_accounts.json
    ├── transactions.json
    ├── billings.json
    ├── periodic_transactions.json
    ├── financial_models.json
    ├── financial_instruments.json
    └── step_interests.json
```
#### Root folder
The root folder contains two different types of files:  
- *SESSION FILES* explained in the [paragraph](#sessions)
- DEVICE REGISTERED with the filename `device_register.json`, containing the list of devices connected to the selected Google Drive. It is useful to understand whether other devices have set a cryptography key and, if not, to export their own, in order to make the data published next available to the allowed instances.

#### Crypto folder
The crypto folder currently contains one file, with the cryptography key to be used to decrypt data. The file content and the format it follows are described in the [cryptography section](#key-saving-system).

#### Preference folder
The preference folder contains the settings configured by the user, which have to be applied throughout the different application instances where the account is saved. 
*An example of a shared preference is whether the device should activate background tasks or notifications.* The format is a simple map containing a key and its corresponding primitive value. The data inside this file is encrypted with the user AES key. 

#### Database folder
Contains all the tables of the user database as JSON files, with all the records translated into maps and gathered in a specific time window, which is explained in the shared preference section. 
All files inside the database folder are encrypted with the user key. 

### Connection steps
A connection with the cloud is meant to be safe and complete so, regardless of the functionality to execute, the cloud connection has some steps to follow:
1. **CONNECTION CONTROL** the application connects to the cloud in order to see whether the space can be locked for the session. When the channel has been reserved, a lock file will be written to prevent other instances from using the same space at the same time. Some errors could be returned by this procedure: 
    - *AUTHENTICATION FAILED* it means the application could not find the Google session to upload
    - *LINE BUSY* so the cloud is currently used by another application instance
    - *NETWORK ERROR* it means the application cannot reach the cloud endpoint.

2. **EXECUTION** the application performs the operation it is expected to do. It starts only after the connection control ends successfully. Other errors could be returned by the procedure.
3. **DISCONNECTION** when the application disconnects, it frees the lock file to make the space available to other application instances. When a logout procedure no longer allows the user to use the cloud, the space occupied by the directory will be emptied if no other device is connected. 
  The disconnection step has to be done regardless of the outcome of the execution step.


## Background tasks
The background part of the application is essential for its success. It mainly checks the services uploaded by the user and checks whether some money has to be received or charged. 
To develop the background status we have to consider different aspects:

### Entities involved
When the background process starts, not all the entities have to be involved. Selecting only the essential parts of the system to take into account will allow the program to execute the task in a faster and more efficient way. In particular, the entities involved are:
- **Account billings** so cashbacks and bank fees. The background task checks, for each bank account, whether the time has come to register the transactions connected to these entities.
- **Periodic transactions** that means periodic incomes and domiciliations. The control procedure is similar to the one applied to the account billings, but it only matters for current accounts.
- **Financial services** without even considering their models. They are available only in savings accounts and it is good to check whether the expiration date has come or whether it is simply time to earn the interest. This procedure involves time deposits and bonds. Stocks are manually regulated by the user.
- **Credit card transactions** this is a crucial operation for credit cards. When an outcome is registered, it does not immediately affect the available balance. Instead, credit cards have to subtract the money the user owes only on a specific day of the month, simulating the function of a credit card provider.

So, when these operations are done, the application does not need to read all the entities saved by the user (such as models or counterparties) and it is necessary to import and export only the data involved in the check. 

### Software scheduling
Background task scheduling is handled in different ways depending on the platform where the application is hosted:
- **workmanager** library provided by Flutter for mobile devices. It is used for iOS and Android instances.
- **Process manager** system used by Windows to handle general processes.
- **crontab** tool to handle scheduled processes, provided by Linux distributions.
It is suggested to configure the background activity on devices that are always active, such as mobile devices. Process handling on desktop devices might not work in the best way due to the frequent start and stop of the device and to the notification handler, which is more evident and visible in a mobile OS. 

**PAY ATTENTION!** *When a background task is scheduled in different application instances, the same job could be done more than once. To avoid this waste of computing, the [background session](#background-session) has been designed to let the device perform the background task only when it hasn't been done yet in the same time window.*

### Cloud implementation
If the cloud implementation is enabled by the user, this functionality will also be provided during background tasks. Since the operation is not done in a foreground environment, the cloud background connection adopts some different methods from the foreground connection. In particular, the background cloud backup implements:
- **Connection attempts** the connection might not work on the first attempt. In a foreground connection an error would be displayed, but in a background connection it is difficult for the end user to see a log, even though it would probably be useful to them. That is why the program allows a minimum number of attempts to retry the connection. 
- **Entities involved** import and export procedures involve only the [entities](#entities-involved) specified above.
- **Disconnection** when the disconnection is done, it will be reported that the background task was completed in the same time window.
